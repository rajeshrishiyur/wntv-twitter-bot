Rocky Goforth — infrastructure program + Bar Raiser (10 items)

RΔ1 · Part 0 — the named operating system. Baseline → one scorecard → numeric gates → root-cause triage → correction verified in cadence. Apple pp4–5.
Drop-in: “My program method is baseline first, one scorecard, numeric gates, first-principles triage, and correction verified by the same number going green.”
RΔ2 · Part 0 — exact gate test. The workbook’s sharper test is not whether a gate exists but whether it can stop work. Apple p4.
Drop-in: “A gate that cannot stop the program is decoration, so I publish the stop line before the first test.”
RΔ3 · Part 0 — red-item contract. Every red arrives with a cause, owner, and date in the same review that surfaced it. Apple p4.
Drop-in: “A red without a cause, an owner, and a date is not status; it is deferred discovery.”
RΔ4 · TMAY ownership probe. Rajesh explicitly separates program machinery from code: he wrote scorecards, BRDs, gates and cadence; engineers built product and automation. Apple p5.
Drop-in: “When I say I, I mean I built the operating system and made the cutover call; engineering built the code.”
RΔ5 · D1 — “gates instead of experience.” Rajesh had never run a WMS migration; the absence of a “trust me” shortcut made written entrance criteria load-bearing. Apple pp28–29.
Drop-in: “I had no experience shortcut to sell, so every phase had to earn entry and exit on written evidence.”
RΔ6 · D2 — rehearsal philosophy. The mock produces the runbook; the live cutover is the next rehearsal with the audience watching. Apple pp30–31.
Drop-in: “A failed mock is cheap; a failed cutover is not—the cutover should feel like the next rehearsal with a larger audience.”
RΔ7 · M1 — instrument silence. The scheduler stopped without emitting a failure, so the permanent control made absence of a heartbeat the alert. Apple pp40–41.
Drop-in: “The process was not wrong; it was silent. We made silence itself the alarm.”
RΔ8 · M1 — the reliability outcome. The next peak being uneventful is framed as an engineered result, not an anticlimax. Apple p41.
Drop-in: “The next peak ran boring, and boring is the reliability deliverable.”
RΔ9 · A3 — why the BRD was the work. The workbook answers the “you only wrote a document” probe directly: complaints become funded, buildable programs through exact specifications. Apple p11.
Drop-in: “Programs die as complaints and ship as documents; my BRD made the operating pain fundable and testable.”
RΔ10 · Part 7 — tool humility. Rajesh’s strongest instrument is the hand-built model and the shared SQL layer, not decorative BI. Apple pp46–47.
Drop-in: “I build in the tool the team reads; I am not a dashboard stylist, but I can interrogate the data underneath it.”

3 · Apple-only story A01 — I1: the LLM triage agent

Allocation note. The current Goforth bank also contains full versions of A01, A02 and A03. They remain here because this task requires the Apple-only stories as a self-contained add-on. Do not tell them twice: A02 to Rocky, A03 to James, A01 to Venkata.

Assigned: Venkata — product judgment, evals, customer trust, unit economics. Company: independent build, not an employer deployment. LPs: Invent and Simplify · Frugality · Dive Deep · Ownership.
LP proof. Invent: routed easy and hard classes differently. Frugality: unit cost was a launch KPI. Dive Deep: graded historical outcomes before model changes. Ownership: built the stack, eval harness and operating rule himself.
60-second pitch. “I built an independent LLM triage agent and treated it as an operations product, not a demo. The naive version cost $25 per incident, and an uncited recommendation made the human repeat the work. I first graded historical incidents into an eval set, then set two release bars: the past must keep passing, and every proposal must cite the ticket and runbook. I routed easy classes to smaller models and reserved expensive calls for the hard tail. Cost fell to $0.40 per incident, a 98% reduction, with accuracy held on the eval set and 100% citation coverage. My regret is that the first eval set grew while early prompts were being judged; I would freeze and version the baseline before the first change.”

S I independently built a Python/FastAPI triage agent for operational incident queues. The naive path produced useful proposals but cost $25 per incident and could answer without a checkable chain of evidence. record

T I needed an operations-grade product: quality held on known cases, every proposal checkable, and unit cost below one dollar—without presenting it as an employer production deployment.

A I graded historical incidents with known-correct triage outcomes before changing prompts or models. I made the eval set the release gate; every prompt, model or routing change had to keep the past passing. I imposed “no citation, no proposal,” binding each action to ticket evidence and a runbook line. I then measured cost by class and routed routine classifications to small models, reserving expensive calls for the hard tail. I reviewed eval accuracy, citation coverage and unit cost together, because optimizing any one alone would create a demo, not a product.

R Cost moved from $25 to $0.40 per triaged incident—a 98% reduction—while accuracy held on the eval set; citation coverage was 100%. record The result was an independently built product with a quality contract and unit economics, not a claim of enterprise adoption.

TRADE-OFF I MADE. I rejected one expensive model for every incident and chose tiered routing. That added routing complexity and eval maintenance, but protected quality while making the unit economics viable.
Failure / learning. The early eval set was still growing while prompts were judged. I would freeze and version the first baseline before the first experiment.
SAFE-SAY. “This was my independent build, not an employer production program: $25 to $0.40 per triaged incident, with quality held on my graded eval set and every proposal cited.”
If asked for source: “Those are my build records as captured in Apple workbook I1, pages 41–42.”

Q1 — How did cost fall without quality falling? Most incidents were easy classes. I proved small models held on those classes against the eval set, then reserved the expensive path for the hard tail.

Q2 — What would break at FBA scale? Access review, data boundaries, eval-set maintenance and drift become programs of their own. I would keep a human approval gate until production evidence beats the human baseline.

20-second version. “I built an independent incident-triage agent with the eval set first and one rule: no citation, no proposal. Routing easy cases to small models moved cost from $25 to $0.40 per incident, a 98% reduction, while eval quality held. I would freeze the first eval version earlier.”

3 · Apple-only story A02 — G1: the UAT that crashed

Assigned: Rocky — strongest real infrastructure failure and Bar Raiser answer. Company: Elementum. LPs: Are Right, A Lot · Earn Trust · Insist on the Highest Standards · Ownership.
LP proof. Are Right: names his wrong reflex and decision. Earn Trust: took the criteria miss to the sponsor as his. Standards: rebuilt UAT around numeric load criteria. Ownership: treats an implicit performance requirement as his gap, not the customer’s fault.
60-second pitch. “Two days before UAT sign-off, five key users had passed all ten end-to-end scenarios on an Elementum track-and-trace app. Then the sponsor opened access more broadly and concurrent logins crashed the system. My first move made it worse: I reran my scenarios, they passed, and I sent screenshots. I was defending my test plan instead of reproducing the customer’s shape. I owned the miss to the sponsor, simulated concurrency with engineering, and the team fixed it, but the sign-off date passed and confidence had to be rebuilt. I permanently changed the UAT contract: every critical scenario gets numeric entrance and exit criteria for uptime, page load and concurrent load at the customer’s user count, volume and network. The later proof that the lesson stuck was a Flexport gate of 500 containers in 20 minutes at 99.6% connectivity before customer testing.”

S On an Elementum track-and-trace application, UAT sign-off was two days away. Five key users had completed ten end-to-end scenarios each, and my test evidence was green. record

T I owned readiness. I needed to earn customer sign-off and protect launch confidence, including requirements the written scenario list had not made explicit.

A When the sponsor said users could not complete a flow, I first reran the same scenarios and sent screenshots showing they passed. That was my central failure: I tried to prove innocence. I then reproduced the customer’s operating shape and found concurrent logins crashed a system my criteria had never load-tested. I told the sponsor the gap was mine—the customer had exposed an implicit performance requirement I failed to surface. Engineering simulated the concurrent load and worked the fix while I rewrote the UAT contract: numeric uptime, page-load and concurrent-load criteria at the customer’s user count, data volume and network, with entrance and exit bars written before testing.

R The sign-off date was missed and trust had to be rebuilt. record The structural correction persisted: a later Flexport launch gate required 500 containers in 20 minutes at 99.6% connectivity before customer testing. record-from-docs I no longer accept “works for us” as readiness evidence.

TRADE-OFF I MADE. After finding the cause, I chose round-the-clock engineering effort and a transparent missed sign-off over relaxing the performance requirement. That spent schedule margin and team capacity, but did not ask the customer to accept an unproven system.
Failure / learning. The actual failure was defensive diagnosis: I mistook my coverage for the truth. The first hour of an escalation now goes to reproducing the customer’s shape, not proving our innocence.
SAFE-SAY. “Five key users passed ten scenarios, but concurrent access crashed the system two days before sign-off; my criteria omitted load, and the deadline was missed.”
If asked for source: “The failure details are Apple workbook G1, pages 43–44; the later performance proof is in the Flexport TPM status source.”

Q1 — Wasn’t the sponsor at fault for opening access broadly? No. Users exercised the system the way their work demanded. Their behavior exposed an implicit requirement my readiness criteria should have surfaced.

Q2 — Why did you send screenshots? Because the scenarios genuinely passed for me, and I confused test coverage with customer truth. That defensive reflex is the behavior I would take back.

20-second version. “Five users passed ten UAT scenarios, but broader concurrent access crashed the system two days before sign-off. I first defended with screenshots—my mistake—then owned that load was absent from my criteria. The date was missed; every gate I run now tests at the customer’s concurrency and volume.”

3 · Apple-only story A03 — B3: two programs, one ruler

Assigned: James — sequencing, shared engineering capacity, process governance and floor adoption. Company: Flexport. LPs: Bias for Action · Deliver Results · Earn Trust · Have Backbone; Disagree and Commit.
LP proof. Bias: made capacity decisions inside a four-week compression. Deliver: compressed program landed and the original date held. Trust: made the collision visible instead of hiding load. Backbone: challenged the resource pull with priced consequences, then committed.
60-second pitch. “Leadership pulled a strategic go-live forward one month and moved engineers off my program to support it. Rather than let two programs run separate escalation systems, I made them one operating problem: one RAID log, one 45-minute daily ruling forum, and one issue grammar—blocker, non-blocker, or requirements gap. True blockers moved through onsite and offshore passes with a written handoff, so issues moved around the clock without asking people to. I escalated only priced decisions: option A costs this; option B costs that. Both programs landed—the compressed one inside four weeks, mine on its original date. About $200K per month per DC was the program-doc value rate. The honest cost was the team’s calendar, and my miss was shipping the ten-step floor guide only a week before cutover. Now operator documentation is an entrance criterion, not a final-week task.”

S At Flexport, leadership advanced a strategic go-live by a month and shared my engineers across that work and my existing launch. Two programs had one team, an immovable date, and about $200K per month per DC at stake in the program record. record

T I had to make the resource collision explicit, protect floor adoption, and land the accelerated program without moving my original date.

A I did not fight the priority after the value was visible; I challenged how it would be executed. I put both programs in one RAID log and one hard 45-minute daily forum. I imposed one grammar—true blocker, non-blocker, or requirements gap—so teams could not win attention by labeling everything urgent. Most alleged blockers were reclassified within a week. True blockers entered a two-pass war room: onsite worked the first pass, offshore continued from a written handoff, and nobody was asked to work continuously. Go/no-go read the true-blocker burn-down to an agreed floor. Escalations went upward the same day as priced choices, not complaints. I also produced a ten-step quick-reference guide for floor adoption.

R The accelerated program landed inside four weeks and my program held its original date. record The defendable economic statement is the program-doc rate—about $200K per month per DC—not a larger cumulative claim. The operating mechanism made shared capacity visible and gave one forum authority over both programs.

TRADE-OFF I MADE. I accepted bounded compression on the team’s calendar and rejected two independent priority systems. The written handoff and time-boxed forum cost coordination effort but prevented an unmanaged slip and continuous heroics.
Failure / learning. The operator guide shipped only one week before cutover, after floor questions had already arrived. Under compression, documentation must be an entrance criterion.
SAFE-SAY. “About $200K per month per DC was at stake—the rate in the program record; the compressed program landed inside four weeks and my original date held.”
If asked for source: “That rate and the operating mechanism are recorded in Apple workbook B3, pages 19–21; I do not inflate the monthly rate into a banked annual claim.”

Q1 — Did you oppose leadership taking your engineers? I made the collision and cost visible, but once the pull-forward was priced it was probably the right business decision. I committed and designed one governance system for both.

Q2 — What actually slipped? No public date slipped. The cost was the team’s calendar and a late operator guide. Naming that cost matters; a “free” compression merely hides where the cost landed.

20-second version. “When two launches shared one team, I ran one RAID log, one 45-minute forum and one blocker grammar. True blockers followed written onsite-to-offshore handoffs. The compressed launch landed inside four weeks, mine held its date, and I learned to make the operator guide an entrance criterion.”

Part 6 in full · G2 — the RF-device script

Best interviewer: Rocky backup; James if asked about training/change control. Company: Sephora. LPs: Are Right, A Lot · Earn Trust · Deliver Results.
Opener. “I missed a training gate because I scored a dependency by effort instead of impact. The script was a small task; its position on the critical path was not.”

S During Sephora’s RP-to-JDA upgrade, training sign-off depended on hundreds of RF guns, printers and workstations being converted. The device team estimated three to four days, so I treated it as low effort and gave it low attention. record

T I owned the readiness chain for an eight-month, dual-DC migration. I had to prove device readiness before training without moving the final go-live.

A I scheduled a device test days before training. The conversion script failed because refreshed RF hardware did not run the old code. My first-principles read was not “the script is buggy”; it was that my risk model was wrong. A small task in front of a go-live exit criterion was a high-impact dependency and had no what-if plan. With key resources on COVID night shifts, the manual fallback could not finish inside the training window. I told leadership the 1.5-week training slip was mine. I then added a what-if and mitigation to every cross-functional dependency regardless of effort and moved proven device readiness into training’s entrance criteria.

R Training slipped 1.5 weeks, but the go-live date held; the broader migration landed on time and about 3% under its roughly $1.8M budget. record The later mock-cutover discipline—7% to 1.8% to 0.3% against a 0.5% line—shows the what-if habit institutionalized.

TRADE-OFF I MADE. I accepted a visible training slip rather than declare unproven devices ready. That consumed scarce SME windows but protected the live date.
Failure / learning. Catching it with my own test saved the go-live; it did not erase the planning failure. Impact, not effort, now decides risk attention.
SAFE-SAY. “Hundreds of devices; a three-to-four-day estimate; device test before training; training moved 1.5 weeks; go-live held.”
If asked for source: “Apple workbook G2, pages 44–45, reconciles two earlier device-count tellings and explicitly tells me to say ‘hundreds.’”

Q1 — Why is the miss yours if the device team estimated it? I accepted an effort estimate as a risk assessment. The impact and lack of fallback were my planning responsibility.

Q2 — Is a 1.5-week training move a big enough failure? G1 is the larger customer-facing miss. G2 matters because small unplanned dependencies are how mature programs fail.

20-second version. “A three-to-four-day device script failed before training because refreshed RF hardware was incompatible. I had scored risk by effort, not critical-path impact. Training slipped 1.5 weeks, go-live held, and proven device readiness is now an entrance criterion.”

S At Flexport I was replacing a manual four-system weekly review with a Snowflake pipeline. The source included ticket data carrying customer content. I scoped the pipeline and correctness gate, but not the data-access security review. record

T I owned the BRD and cutover. I had to complete the access review without skipping the Monday operating review or weakening the one-percent parity gate.

A When the review surfaced mid-build, I owned the two-week miss upward as a scoping failure, not “slow security.” I had treated approval as a formality instead of a lead-time workstream. I re-sequenced rather than bypass it: the manual path stayed live during the parallel run, so the review continued every Monday. I documented the cross-reference table, named the data classes and made read access explicit. I then changed the kickoff checklist permanently: security has an owner and lead time in the BRD, and every data program starts by asking whose approval the data needs and how long it takes.

R The access review cost two weeks of schedule margin, but no weekly review was skipped. The pipeline cut over only after manual and automated metrics agreed within one percent for consecutive weeks, and system accuracy closed at 90% from a 60% baseline. record The miss cost margin, not delivery.

TRADE-OFF I MADE. I kept the labor-intensive manual path alive and rejected a premature cutover. That spent two more weeks of my time but preserved delivery and access integrity.
Failure / learning. The parallel run saved me partly by luck—it was designed for correctness, not schedule resilience. Now I deliberately keep the old path until the new path clears both access and correctness.
SAFE-SAY. “I under-planned the customer-data access review by two weeks; the manual path kept every Monday review alive, and cutover still waited for one-percent parity.”
If asked for source: “Apple workbook G3, pages 45–46, and A3; the two-week miss and parity gate are record, not modeled.”

Q1 — Why call a two-week slip a failure? Because the cause was structural. Every customer-data program needs approval; absent a checklist change, I would repeat the miss.

Q2 — Why not ask for an exception? Customer-content access was a gate. Bypassing it would convert a schedule miss into a trust and compliance risk.

20-second version. “I discovered a customer-data security review mid-build and lost two weeks because it was absent from my BRD. The manual path kept the weekly review alive; cutover still waited for one-percent parity. Security lead time is now planned at kickoff, never discovered.”

Part 0 in full · “How I run a program”

Say this in 35 seconds. “I use the same five-part system on every program. First, baseline the KPI before touching the process. Second, publish one scorecard on one cadence with a grain and date on every number. Third, write numeric entrance and exit criteria that can actually stop the program. Fourth, when a number goes red, trace it to the root before spending money on the symptom. Fifth, put the cause, owner and date into the same cadence, then use the same number to prove the fix went green.” Apple pp4–5.
