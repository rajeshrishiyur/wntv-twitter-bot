1. Architecture — nine stages, left to right

Looker does not hold the book of record. The warehouse does. Looker stores LookML, users, saved content, and a result cache, and it generates SQL at query time. A persistent derived table is still a table in the warehouse. The fix never lands in Looker.

Read the top row left to right, then the bottom row left to right. Red boxes are where a data-integrity PM owns the definition: the tests, the measure, and the rule that the tool must not write the fix. Aggregate awareness sits in stage 4 so a program total can use a rollup and a drill to the PO line still hits the base table. The lab model does not declare a rollup; the five tiles each query the explore whose grain matches the question.

3. Data model and the lab’s LookML

Reconciliation is counted at the PO line. An asset with no line, and a line with two assets, are both real, and neither is allowed to change the denominator by accident. The explores below are the ones in capex_integrity.model.lkml. They are not a new model.

The star is the po_lines explore. Program, site, and supplier are many-to-one and are not on the fan-out path. dim_input_owner is not joined here: the owner is per field, and putting the owner on this explore would sit on the asset join. Three other explores stay off this star so they cannot multiply the 40: exceptions (the aging PDT), completeness (one row per asset per field), and assets (first-time-right, so orphan AST-TS-0040 stays in the denominator). field_edits is a fourth, one row per program per field, and it does not listen to the site filter.

Fan-out and the symmetric aggregate. Line 00018 has quantity 2 and two assets. A plain count on the joined explore is 41 for the program. That measure is in the view as plain_row_count_do_not_certify with hidden: yes. Dividing assets by lines is 39/40 = 97.5%, because the second asset on 00018 hides one of the two in-transit lines (00039 and 00040). That measure is hidden too. The certified rate counts distinct lines on both sides: lines with at least one asset, over lines. Looker can protect a count_distinct of the primary key from the fan-out. A ratio you write by hand is not protected, so both the numerator and the denominator are count_distinct. There is no default filter on received date. Hiding nulls would turn 38/40 into 38/38. From the PO explore the orphan disappears and first-time-right becomes 21/39. The assets explore keeps 21/40. lab

# fact_po_line.view.lkml — both sides count_distinct. TS-LINE-RAMP is 38/40 = 95.0%.
measure: lines_with_an_asset {
  type: count_distinct
  sql: ${po_line_id} ;;
  filters: [fact_asset.asset_id: "-NULL"]
}
measure: reconciliation_rate {
  type: number
  sql: 1.0 * ${lines_with_an_asset} / NULLIF(${po_line_count}, 0) ;;
  value_format_name: percent_1
  description: "Certified definition: distinct PO lines with at least one asset, divided by distinct PO lines. TS-LINE-RAMP is 38/40 = 95.0%. Not assets divided by lines."
}
# capex_integrity.model.lkml — same block on po_lines, exceptions, completeness, field_edits, assets.
# Priya: TS-LINE-RAMP, PACK-CELL-EXP, FIXTURE-REUSE-24. Jordan: TS-LINE-RAMP only.
access_filter: {
  field: dim_program.program_id
  user_attribute: program_ids
}
join: fact_asset {
  type: left_outer
  relationship: one_to_many
  sql_on: ${fact_po_line.po_line_id} = ${fact_asset.po_line_id} ;;
}

The aging PDT. Age is not a column on fact_exception. exception_aging in fact_exception.view.lkml is a derived table Looker persists in the warehouse. It keeps closed_date null, subtracts opened_date from the lab as-of (16 March 2026, not the wall clock), and buckets the day count. Open counts before the fix are 7 / 7 / 7. Closing EX-PIS-00017 removes one row from 0–7 on the next rebuild, so the counts become 6 / 7 / 7. The datagroup is sql_trigger: SELECT MAX(created_at) FROM capex.fact_asset and max_cache_age: "24 hours". A correction of an existing asset does not by itself move created_at. The warehouse job has to touch a watermark that trigger reads, or the tile waits for the 24-hour cap.

# exception_aging PDT — open rows only. Age 7 is still 0-7. Age 8 is 8-30.
DATE_DIFF(p.as_of_date, e.opened_date, DAY) AS age_days,
CASE
  WHEN DATE_DIFF(p.as_of_date, e.opened_date, DAY) <= 7 THEN '0-7'
  WHEN DATE_DIFF(p.as_of_date, e.opened_date, DAY) <= 30 THEN '8-30'
  ELSE '31+'
END AS aging_bucket
... WHERE e.closed_date IS NULL

6. How to say it

Sixty seconds — walk the flow, then stop

TS-LINE-RAMP is forty PO lines leaving two CM trackers for one system of record. At six a.m. dbt lands them, trims and types, conforms site codes, and quarantines against a tolerance published before the files arrived. Looker stores LookML, not the rows. Reconciliation is distinct lines with an asset over distinct lines: 38 over 40, 95 percent. Line 00018 has two assets, so a raw count would lie. Line 00017 is tagged with a blank placed-in-service date: twelve missing, completeness 70 percent, reconciliation still 95. Under the lab’s 98 percent line the alert fires, and a Looker Action opens Finance a task with the drill link. Looker cannot write the date. The next run shows eleven missing and aging six, seven, seven. First-time-right stays 21 of 40. The playbook quarantines a blank date on the next file.

Proficiency — say this, then stop

I wrote seven metric definitions and specified the Looker SQL Runner queries for the Zendesk-to-Snowflake pipeline. The infrastructure team built it. The weekly-review metrics I ran were in Excel and in SQL. I have not built a dashboard hands-on in Looker, Tableau, or Power BI.

Ask, if they use a BI tool

Ask, about freshness

Ask, about change control
