4. Define the metrics once

What. Read the view files in lookml/ next to sql/03_metrics.sql. A dimension is something you group or filter by: program, site, owner, a date. You do not sum it. A measure is an aggregate: a count distinct, or a ratio of two of those. The primary key on fact_po_line is po_line_id. count_distinct of that key is a symmetric aggregate: Looker will not let the one-to-many asset join multiply it. type: count counts joined rows. A ratio you type by hand is not protected.

Five follow-ups

Why is the PO line the grain? Because the failure you are managing is a buy with no asset, and an asset-grain table cannot show a row that was never tagged. Two assets on one line are still one line. The orphan is a different check, on the asset, and it does not get to fill the reconciliation hole.

Why Looker rather than Excel for this? Excel holds the rows. It does not hold a definition. The next copy of the file is a second meaning of reconciled, and it will turn 00017 into a number if someone saves it. Looker, if that is the tool they have, keeps the measure in Git and queries the warehouse. Looker Studio can draw the tiles and will not give you that Git history. I would not pretend those are the same product. I have not shipped either model. I have frozen definitions and a parity gate, with SQL Runner named as the surface.

How do you stop two definitions of reconciled? One measure in the view, count distinct on both sides, reviewed like code. The asset version and the received-only version stay in the repo as hidden measures so someone can see the trap, and they are not on the tile. The Monday schedule and the alert both point at the certified measure. A side file that divides assets by lines ordered is a different metric, and it does not replace the tile without a change to the view.

What would you not automate yet? I would not let a model fill placed-in-service, the reuse source, or the program allocation. Those are judgments, and this program’s first-time-right is 52.5 percent. I would not train anything on a queue that still has duplicate serials and an orphan. I would automate the gate that is already a rule: trim, parse the date, map the site, reject a blank key, reject an unknown site, reject a line that is not on the equipment list. Capitalization and reuse stay with Finance and the AME until the scorecard says the input is trustworthy.

How does this map to onboarding playbooks? The pilot is this program. The playbook entry is the reject we added after the scorecard found the blank date. The next program inherits the rule, the owner map, the tolerance, and the same five tiles. What stays local is the equipment list and the CM’s site codes, which still have to be mapped. I would ask, on the pilot that became their playbook, which lesson teams actually followed and which one they had to keep enforcing.
